# ADR-0002：單人經典模式規則設計評估——計分機制與遊戲流程（2026-08）

## 狀態

延續 [0001](./0001-classic-mode-review.md) 的性質：**這是評語與健檢，不是行動計畫**。文中「後續可考慮方向」不是承諾要做的待辦。

## 背景（Context）

0001 評估的是「經典模式現況整體滿意度」；這篇聚焦更窄——單獨評估**計分機制**與**遊戲流程**這兩條規則本身設計得好不好。過程中除了確認設計意圖，也在調查中發現兩個實際的程式錯誤（非設計取捨），一併記錄在此。

## 已確認的設計決策（合理，非技術債）

### D3. 計分權重是憑直覺訂定的

- `+`/`-` 各1分、`×`2分、`÷`3分，`≥2個×`或`≥2個÷`各額外+1分（見 [specs/scoring.spec.md](../../specs/scoring.spec.md)）。
- 確認：這套權重沒有參照特定資料或其他遊戲，是憑直覺抓的相對難度排序（除法主觀感覺比加減難算）。

### D4. 必須用滿當前全部手牌（恆為4張）才能出牌

- `playCard()` 要求 `numberCardIds.length === handCardCount`（[lib/classic-single-play-engine.ts:217-218](../../lib/classic-single-play-engine.ts)），UI 端也有防呆（[classic-play-game.tsx:479-486](../../app/single-play/[mode]/classic-play-game.tsx)）。
- 確認：這是24點遊戲本身的基礎規則（一手牌對應一個完整答案），不是從多人拉密模式隨便搬過來的，是刻意保留的 genre 慣例。

### D5. 答錯零懲罰、零具體錯誤提示

- 答錯時 `room` 完全不變、不扣分、不限次數，只顯示同一句 toast「答案不等於 24」，不區分是語法錯還是算出來不是24（[useGameActions.ts:108-113](../../hooks/useGameActions.ts)）。
- 唯一代價：打斷連勝計數（`resetConsecutiveWins()`）。
- 確認：刻意設計，配合「無時限」的休閒定位，讓玩家可以無壓力反覆試。

### D6. 跳過（skip）無限次、整手換牌、零代價

- `skipHand()` 不是丟1張補1張，是**整手4張全部捨棄重抽**（[classic-single-play-engine.ts:338-379](../../lib/classic-single-play-engine.ts)），沒有次數上限，不扣分、不打斷連勝。
- 確認：刻意設計，理由是「題目保證有解，跳過＝玩家選擇不解這一手」，不是漏洞。

## 已確認的實際缺陷（Known Defects，非設計取捨）

以下兩點是程式邏輯錯誤，記錄事實與影響範圍，本次先不修，之後由專案維護者決定是否開 GitHub issue追蹤。

### B1. `speed_win` 成就實質失效

- `markTurnStart()`（[useGameActions.ts:118-120](../../hooks/useGameActions.ts)）定義了、也在 [useSinglePlay.ts:39](../../hooks/useSinglePlay.ts) 解構取出，但**全專案沒有任何地方實際呼叫它**。
- 結果：`turnStartTimeRef.current` 只在整局遊戲第一次 mount 時設定一次，之後永遠不重置。`speed_win`（出牌用時 ≤10秒解鎖）實務上幾乎只能在整局第一手解鎖，第二手以後幾乎不可能再觸發。
- 影響範圍：只影響成就解鎖，不影響分數或排行榜。優先度較低。

### B2. `[3,3,8,8]` 手牌會被判定「有解」但玩家永遠答不出來

- 引擎用容差比對 `Math.abs(x-24) < 1e-6`（`canMake24()`，[lib/daily-seed.ts:34-50](../../lib/daily-seed.ts)）判斷一手牌「有解」才會實際發給玩家；但 `playCard()` 驗算用嚴格 `answer === 24`（[classic-single-play-engine.ts:218](../../lib/classic-single-play-engine.ts)），沒有任何容差。
- `[3,3,8,8]` 唯一解法 `8÷(3-8÷3)` 用 mathjs 算出來是 `23.99999999999999`（浮點誤差），永遠不會等於24。若玩家真的抽到這手牌，無論怎麼想都不可能過關——玩家會以為自己數學不對，實際上是程式判準不一致。
- 其他手牌（如 `[1,2,3,8]`、`[1,2,12,13]`）也有類似浮點誤差解法，但那些牌另有精確整數解可走，玩家不會被卡死；只有 `[3,3,8,8]` 是唯一已知的死路。
- 影響範圍：會讓玩家卡在一手牌解不開、體感是「遊戲壞了」。優先度高於 B1。
- 最小修法方向（僅供之後參考，非本次待辦）：讓 `playCard()` 的相等判斷跟 `canMake24()` 用同一套容差。

## 設計張力（Emergent Tension，非bug，非決策，是兩個各自合理的規則疊加後的意外空間）

### T1. 便宜解法 vs 貴解法並存 + 跳過零代價 → 分數深度可被繞過

- 已用 `[2,3,4,6]` 實測驗證：同一組4個數字常常同時存在多個分數等級的解法（該例同時存在4分/6分/8分三種可行解），玩家只需要找到便宜解法就能過關拿低分，完全不需要去找貴解法（除非為了「完美手」加成才會多想）。你確認過設計時沒特別想過這層張力（Q3）。
- 同時，跳過是零代價、無限次、題目保證有解（D6，你確認是刻意設計，理由合理）。
- **兩者疊加**：玩家如果真心想衝高分/完美手次數，最佳策略不是「認真解每一手」，而是「跳過直到湊到一手一眼就能看出貴解法的牌，再出牌拿完美手」。這不是bug——D6單獨看是合理的（跳過本來就該是免費選項），T1單獨看也只是「同一手牌本來就有多解」的數學事實——但兩者合在一起，讓計分機制原本想鼓勵的「玩家願意多想一下去找貴解法」這個行為，變成可以被「用跳過篩牌」完全繞過，score的策略深度因此沒有被真正兌現。

## 綜合評語

規則設計整體是**「足以撐起一個無壓力、隨拿即玩的休閒24點遊戲」**，跟你刻意選擇的低摩擦調性（D4/D5/D6）是一致、自洽的。遊戲流程本身沒有明顯的設計錯誤：出牌／跳過／答錯的邊界都處理得乾淨，唯一的兩個問題（B1/B2）是實作疏漏，不是流程規則本身的毛病。

計分機制則有一個沒被兌現的設計意圖：三個運算符權重（尤其÷=3分＋≥2個÷的bonus）明顯是想鼓勵玩家去找「更貴」的解法，但因為（a）便宜解法通常同時存在且更容易被第一時間看到，（b）跳過完全免費、可以無限次篩牌，這套權重實際上**很容易被繞過而不是被追求**。願意主動找貴解法的玩家，多半是為了「完美手」這個額外機制，而不是基礎計分本身在引導——換句話說，基礎計分權重（D3）目前更像是一個「事後算分的度量」，而不是一個真正在遊戲過程中引導玩家決策的機制。這不代表規則設計得不好，而是**分數的策略深度沒有被玩法結構撐起來**：分數會因為解法不同而不同，但玩家沒有被任何規則推著去追求那個更高的分數。

兩個bug（B1/B2）進一步削弱這個系統的可信度：`speed_win`基本上是個裝飾性成就，`[3,3,8,8]`則會讓少數玩家真的卡死在一局遊戲裡，體感上是「遊戲壞了」而不是「我數學不夠好」，這種情況在一個以益智為賣點的遊戲裡，殺傷力比表面上看起來更大。

## 後續可考慮方向（僅供規劃參考，非承諾）

- B2 建議之後開 issue 優先處理（會讓玩家卡死），B1 優先度較低（只影響一個成就的裝飾性效果）。
- 若未來想讓計分機制的深度真的影響玩法（而不只是事後算分），可以想想要不要讓「跳過」跟「完美手資格」產生某種關聯——但這只是舉例，不是建議現在做，且要小心不要讓跳過因此變得有壓力，違背 D6/D5 想要的無壓力調性。
